# 应用资源消耗分析

一个 Streamlit 页面，用于分析应用资源消耗 Excel 数据。约定第一个 sheet 为系统信息，其余每个 sheet 表示一个测试场景，sheet 名会作为场景名，例如“轻载”“重载”“冷启动”“后台空闲”。

## 适用场景

这个工具适合用来查看一个应用在不同使用场景下的资源消耗表现，例如：

- 轻载、重载、空闲、冷启动、长时间运行等场景对比
- CPU、内存、线程、句柄、IO 的趋势观察
- 找出峰值、P95、超阈值异常点
- 对比不同场景、不同版本的资源压力差异
- 基于长时间资源数据推导最低运行配置和推荐配置
- 在还没有真实采集数据时，用示例数据先调试分析流程

## Excel 数据结构

工作簿按 sheet 拆分：

| Sheet 位置 | 含义 | 说明 |
|---|---|---|
| 第 1 个 sheet | 系统信息 | 展示用，不参与指标计算 |
| 第 2 个及之后 | 场景数据 | 每个 sheet 一个场景，sheet 名就是场景名 |

示例：

| Sheet 名 | 类型 |
|---|---|
| 系统信息 | 系统信息 |
| 轻载 | 场景数据 |
| 重载 | 场景数据 |
| 后台空闲 | 场景数据 |

## 场景数据字段

场景 sheet 会先自动识别以下核心表头：

- 时间戳
- CPU%
- 内存占用（MB）
- 系统总内存
- 内存占用百分比
- 线程
- 句柄
- io

字段名可以是中英文近似名称，页面会尽量自动映射。例如 `CPU%`、`cpu`、`内存占用（MB）`、`memory`、`thread`、`线程` 这类名称都可以识别。

除了核心字段外，页面还会优先识别一组语义化扩展字段：`QPS`、`TPS`、`任务数`、`并发数`、`响应时间(ms)`、`错误数`、`FPS`、`卡顿次数`、`GC次数`、`GC耗时(ms)`、`堆内存(MB)`、`网络上行(KB/s)`、`网络下行(KB/s)`、`请求数`、`失败请求数`、`重试次数`、`磁盘读(MB/s)`、`磁盘写(MB/s)`、`IOPS`、`IO等待(ms)`。

这些语义化字段会进入趋势、对比、基准增长、分布、相关性、异常、报告和资源效率分析。场景 sheet 中其他可以转成数值的列仍会被自动识别为“动态扩展指标”，例如 `GPU%`、`自定义耗时`、`业务队列长度` 等。

配置建议仍只使用 CPU、内存、线程、句柄、IO 这些语义明确的核心指标；业务字段主要用于效率、体验和稳定性判断。

推荐字段格式：

| 字段 | 类型 | 示例 | 说明 |
|---|---|---|---|
| 时间戳 | 时间 | `2026-06-13 09:00:00` | 用于趋势图横轴 |
| CPU% | 数值 | `36.5` | CPU 使用率 |
| 内存占用（MB） | 数值 | `1024.8` | 应用占用内存 |
| 系统总内存 | 数值 | `16384` | 单位 MB，用于补算内存占比 |
| 内存占用百分比 | 数值 | `6.25` | 如果缺失，会尝试用内存占用 / 系统总内存计算 |
| 线程 | 数值 | `68` | 线程数量 |
| 句柄 | 数值 | `1200` | 句柄数量 |
| io | 数值 | `3.4` | IO 指标，具体单位按采集工具定义 |
| QPS / TPS | 数值 | `120.5` | 业务吞吐，用于计算单位资源成本 |
| 并发数 | 数值 | `80` | 并发用户、连接或任务数 |
| 响应时间(ms) | 数值 | `235.8` | 响应质量指标 |
| FPS / 卡顿次数 | 数值 | `58.2`、`1` | 客户端渲染体验 |
| GC次数 / GC耗时(ms) / 堆内存(MB) | 数值 | `3`、`45.6`、`512` | 运行时回收压力 |
| 网络上行/下行(KB/s) | 数值 | `120`、`860` | 网络吞吐 |
| 请求数 / 失败请求数 / 重试次数 | 数值 | `1000`、`2`、`1` | 请求稳定性 |
| 磁盘读/写(MB/s) / IOPS / IO等待(ms) | 数值 | `20.5`、`8.2`、`320`、`12` | 磁盘压力 |
| 其他数值列 | 数值 | `GPU%`、`队列长度` | 自动作为动态扩展指标 |

## 运行

首次运行先安装依赖：

```bash
python3 -m pip install -r requirements.txt
```

生成一份调试用 Excel：

```bash
python3 generate_sample_data.py
```

启动页面：

```bash
streamlit run app.py
```

打开浏览器访问：

```text
http://localhost:8501
```

如果没有上传 Excel，页面默认读取 `data/sample_resource_consumption.xlsx`。上传自己的 Excel 后，会以上传文件为准。页面支持一次上传多个 Excel，用于对比不同版本、不同构建或不同测试批次。

## 页面功能

### 1. 概览

展示当前筛选范围内的整体情况：

- 场景数
- 样本数
- CPU 峰值
- 内存峰值
- 告警点数量
- 每个场景的均值、峰值、P90、P95、P99、波动性、趋势斜率、超阈次数、超阈占比、最大连续超阈

这里适合快速判断哪个场景最重、是否存在明显资源峰值，以及超阈是短暂尖峰还是持续压力。

### 2. 趋势

按时间展示指标曲线，支持多场景叠加：

- CPU
- 内存占用
- 内存占比
- 线程
- 句柄
- IO
- Excel 中自动发现的其他数值指标

每个趋势图都会显示对应阈值线，方便观察资源是否持续超标，还是只有短时间尖峰。

### 3. 对比

对不同场景做横向柱状图对比，支持选择：

- 均值
- 峰值
- P90
- P95
- P99
- 标准差
- IQR
- 变异系数
- 趋势斜率

这个页面适合回答“轻载和重载差多少”“哪个场景内存压力最大”“哪个场景 CPU P95 更高”这类问题。

### 4. 配置建议

基于当前筛选数据推导软件的最低运行配置和推荐配置。

需要输入：

- 测试机 CPU 核数
- 目标 CPU 利用率上限
- 最低 CPU 核数下限
- 系统和后台预留内存
- 最低内存下限
- 最低磁盘剩余空间
- 推荐配置安全系数

输出：

- 最低可运行配置
- 推荐配置
- CPU 核数
- 内存容量
- 磁盘建议
- 推导说明和数据不足风险

CPU 核数估算使用当前筛选数据的 CPU P95：

```text
CPU原始需求 = 测试机核数 × CPU P95 / 目标CPU利用率上限
```

例如测试机是 8 核，CPU P95 为 56%，希望目标机器长期 CPU 不超过 70%：

```text
CPU原始需求 = 8 × 56% / 70% = 6.4 核
```

然后向上取常见核数档位，例如 8 核。推荐配置会在最低配置基础上再乘以安全系数。

内存估算使用应用内存峰值：

```text
最低内存需求 = 应用内存峰值 + 系统和后台预留内存
```

然后向上取常见内存档位，例如 4GB、8GB、16GB、32GB。

这个结论适合做初步配置建议。正式发布最低配置前，建议在目标低配机器上跑关键场景和长稳场景验证。

### 5. 基准增长

选择一个场景作为基准，自动计算其他场景相对基准的增长率。

支持：

- 选择基准场景
- 选择均值、峰值、P90、P95、P99、波动性或趋势斜率作为计算口径
- 查看核心指标和动态扩展指标的相对增长率
- 用柱状图观察指定指标的增长幅度

增长率计算方式：

```text
(当前值 - 基准值) / 基准值 * 100%
```

这个页面适合回答“重载比轻载高多少”“新场景相比基准场景是否明显退化”。

### 6. 泄漏检测

对每个数据源和场景的内存占用做线性回归，计算内存随时间增长的斜率；同时对所有可用指标输出趋势斜率和首尾变化。

输出字段：

- 内存斜率：单位 MB/分钟
- R2：线性拟合程度
- 首尾增长：最后一个采样点和第一个采样点的内存差
- 判断：数据不足、无明显增长、轻微增长、疑似泄漏
- 全指标趋势斜率：CPU、内存、线程、句柄、IO 和动态扩展指标的变化速度

侧边栏可以配置“内存疑似泄漏斜率阈值”。当前判断逻辑是：内存斜率达到阈值，并且线性趋势较明显时，标记为疑似泄漏。

### 7. 版本对比

上传两个或更多 Excel 后，可以按数据源对比不同版本。

支持：

- 按场景对比不同 Excel 文件
- 选择 CPU、内存、线程、句柄、IO 等指标
- 选择均值、峰值、P90、P95、P99、波动性或趋势斜率作为统计口径
- 表格和分组柱状图展示
- 选择基准数据源，按增长阈值自动判断是否退化

这里的数据源名称来自上传文件名；使用示例数据时，数据源名为“示例数据”。

### 8. 资源效率

把资源消耗和业务负载绑定，输出单位吞吐或单位并发下的资源成本。

支持：

- 自动选择 QPS、TPS、任务数或请求数作为吞吐口径
- 计算 CPU P95 / 吞吐
- 计算内存峰值 / 并发
- 计算 IO、网络、磁盘相对吞吐的单位成本
- 计算失败率和每千请求错误数
- 用柱状图对比不同场景或不同数据源的效率指标

这个页面适合判断“资源上涨是否真的退化”。例如 CPU 变高但 QPS 增长更多时，单位吞吐 CPU 成本可能反而下降。

### 9. 决策

把已有指标转换成更直接的测试结论。

支持：

- 场景风险评级：综合超阈、连续超阈、内存趋势、失败率、响应时间、FPS 等规则输出低/中/高风险
- 发布门禁：可配置允许最高风险等级、疑似泄漏是否失败、任意超阈是否失败、请求失败是否失败
- 稳定性评分：按场景给出 0-100 分评分和扣分原因
- 瓶颈提示：粗略提示 CPU、内存、IO、网络、业务错误/重试等方向
- 容量估算：基于当前单位资源成本，按目标吞吐外推 CPU 核数和内存建议

这个页面适合回答“这轮测试能不能过”“哪个场景最危险”“下一步应该优先看哪个瓶颈”。

### 10. 分布

包含两个视角：

- 箱线图：查看每个场景的指标分布、离群点和波动范围
- 相关性热力图：查看 CPU、内存、线程、句柄、IO 之间是否存在明显相关关系

### 11. 异常

根据侧边栏配置的阈值找出超标采样点。

支持：

- 查看异常点时间、场景、指标、值、阈值
- 下载异常点 CSV

### 12. 报告

自动生成测试结论和报告。

当前报告包含：

- 阈值告警概况
- 决策分析、发布门禁、稳定性评分和瓶颈提示
- 告警持续性摘要
- 各指标峰值出现的数据源和场景
- 内存趋势检测结论
- 汇总数据
- 内存趋势检测表
- 全指标趋势斜率
- 资源效率分析
- 最低运行配置和推荐配置
- 分析口径说明

支持下载：

- Markdown 报告
- HTML 报告

如果需要 PDF，可以先下载 HTML，再用浏览器打印为 PDF。原生 PDF 导出可以后续根据部署环境补充。

### 13. 系统信息

展示 Excel 第一个 sheet 的内容。这个 sheet 不参与数值分析，主要用于记录：

- 应用名称
- 版本
- 测试设备
- 操作系统
- CPU
- 系统内存
- 采样间隔
- 测试说明

### 14. 原始数据

展示经过字段映射后的场景数据，支持按当前场景筛选结果导出 CSV。

## 侧边栏配置

侧边栏包含三类配置：

| 配置 | 说明 |
|---|---|
| 数据源 | 上传一个或多个 Excel，或使用本地示例数据 |
| 自定义字段映射 | 为每个标准字段配置额外别名，适配不同采集工具 |
| 阈值 | 配置核心指标和动态扩展指标的告警阈值 |
| 指标方向 | 配置每个指标是“越高越差”还是“越低越差” |
| 稳定区间 | 排除每个场景开头 N 分钟，避免启动预热影响统计 |
| 筛选 | 选择要分析的数据源、场景和趋势图指标 |

阈值只影响告警点、超阈次数和趋势图阈值线，不会修改原始数据。

动态扩展指标默认阈值使用当前数据的 P95。对于 FPS、成功率这类“越低越差”的指标，可以在侧边栏把告警方向改成“越低越差”。

稳定区间会影响页面上的统计、趋势、对比、异常和报告。原始 Excel 不会被修改。

## 分析口径

当前实现使用以下统计口径：

| 指标 | 含义 |
|---|---|
| 均值 | 当前场景全部采样点的平均值 |
| 峰值 | 当前场景全部采样点的最大值 |
| P90 | 90 分位值，用于观察较高水位 |
| P95 | 95 分位值，用于观察大部分时间内的高水位 |
| P99 | 99 分位值，用于观察尾部风险 |
| 超阈次数 | 指标值大于侧边栏阈值的采样点数量 |
| 超阈占比 | 超阈采样点数量 / 有效采样点数量 |
| 最大连续超阈 | 同一指标连续处于超阈状态的最长时间 |
| 峰值发生时间 | 指标峰值相对当前场景起始时间的偏移 |
| 标准差 / IQR / 变异系数 | 衡量指标波动性 |
| 相对增长率 | 当前场景统计值相对基准场景的增长百分比 |
| 趋势斜率 | 指标对时间做线性回归后的增长速度，单位为指标值/分钟 |
| 内存斜率 | 内存占用对时间做线性回归后的增长速度，单位 MB/分钟 |
| CPU P95/吞吐 | CPU P95 除以 QPS、TPS、任务数或请求数，用于衡量单位吞吐 CPU 成本 |
| 内存峰值/并发 | 内存峰值除以平均并发，用于衡量单位并发内存成本 |
| 失败率 | 失败请求数 / 请求数 |
| 每千请求错误数 | 错误数 / 请求数 × 1000 |
| 风险评分 | 综合超阈、连续超阈、泄漏、失败率、响应时间、FPS 等规则生成的风险分 |
| 发布门禁 | 按风险等级、疑似泄漏、超阈、请求失败等规则输出通过 / 不通过 |
| 稳定性评分 | 100 分制评分，按风险评分扣分 |
| 容量估算 | 按当前 P95 单位资源成本，对目标吞吐做线性外推 |
| 瓶颈提示 | 根据 CPU、内存、IO、网络、响应时间和错误率粗略提示排查方向 |
| CPU核数估算 | 测试机核数 × CPU P95 / 目标CPU利用率上限 |
| 内存配置估算 | 应用内存峰值 + 系统和后台预留内存 |

P95 相比峰值更适合判断稳定压力，因为峰值可能只是一次瞬时尖峰。

## 核心算法说明

### 动态指标发现

页面读取每个场景 sheet 时，会分两步处理字段：

```text
第一步：把时间戳、CPU、内存、线程、句柄、IO 等核心字段映射成内部标准字段
第二步：扫描剩余列，能转成数值的列自动加入动态扩展指标
```

例如 Excel 中有这些列：

```text
时间戳, CPU%, 内存占用（MB）, FPS, 响应时间(ms), 网络下行(KB/s)
```

其中 `CPU%` 和 `内存占用（MB）` 会进入核心指标，`FPS`、`响应时间(ms)`、`网络下行(KB/s)` 会进入动态扩展指标。

动态扩展指标的内部字段名会加上 `extra::` 前缀，用来避免和核心字段冲突；页面展示时仍使用原始 Excel 列名。

动态指标默认假设“越高越差”，例如响应时间、错误数、网络流量通常适用这个方向。对于 FPS、成功率这类“越低越差”的指标，需要在侧边栏手动调整告警方向。

### 分位数统计

资源分析中会同时看均值、峰值和 P95。

均值用于观察整体负载水平，但它会掩盖短时间高峰；峰值用于定位极端情况，但它可能只是一次很短的尖峰；P95 表示 95% 的采样点都不超过这个值，更适合描述“多数时间内的高水位”。

示例：

```text
CPU采样值排序后，取位置 95% 处的值，即 CPU P95
```

如果一个场景 CPU 均值是 30%，峰值是 98%，P95 是 62%，通常说明大部分时间压力可控，但存在瞬时尖峰。配置建议会优先参考 P95，同时把峰值作为风险提示。

### 阈值告警

每个指标都有一个可配置阈值，例如 CPU 80%、内存 2048MB、线程 120。

告警点计算方式：

```text
越高越差：超阈次数 = 指标值 > 阈值 的采样点数量
越低越差：超阈次数 = 指标值 < 阈值 的采样点数量
```

它适合回答两个问题：

- 是否超过了预设资源红线
- 超过红线是偶发，还是持续发生

如果只是峰值超阈 1 次，风险通常低于连续大量采样点超阈。

### 稳定区间

启动阶段经常会出现加载、缓存、初始化造成的资源尖峰。稳定区间功能可以排除每个场景开头 N 分钟。

处理方式：

```text
每个数据源 + 每个场景分别找到最早时间戳
只保留 时间戳 >= 最早时间戳 + N分钟 的数据
```

这样可以把“启动预热阶段”和“长期稳定运行阶段”分开看，避免启动尖峰影响长稳结论。

### 基准增长率

基准增长用于比较不同场景或不同版本相对某个基准的变化。

计算方式：

```text
相对增长率 = (当前值 - 基准值) / 基准值 * 100%
```

其中“当前值”和“基准值”可以选择均值、峰值或 P95。

示例：

```text
轻载 CPU P95 = 30%
重载 CPU P95 = 60%
相对增长率 = (60 - 30) / 30 * 100% = 100%
```

这表示重载场景的 CPU P95 相比轻载翻倍。

### 内存泄漏趋势检测

内存泄漏检测不是只看内存峰值，而是看内存是否随时间持续上升。

当前实现对每个“数据源 + 场景”的内存占用做一元线性回归：

```text
内存占用 = 斜率 × 运行分钟数 + 截距
```

输出：

- 内存斜率：单位 MB/分钟
- R2：线性趋势拟合程度
- 首尾增长：最后一个采样点减第一个采样点

判断逻辑：

```text
如果斜率 >= 配置的疑似泄漏阈值，并且 R2 >= 0.35，则标记为疑似泄漏
如果斜率 > 0 但未达到阈值，则标记为轻微增长
如果斜率 <= 0，则标记为无明显增长
```

这个算法适合发现“长时间运行越来越占内存”的问题。它不能替代代码级泄漏定位，但能快速判断哪些场景需要进一步排查。

### 多文件版本对比

上传多个 Excel 后，页面会把每个文件名作为数据源。

对比方式：

```text
按 数据源 + 场景 分组
分别计算每个指标的均值、峰值、P95
再按场景横向比较不同数据源
```

这适合比较不同版本、不同构建、不同测试批次之间是否发生资源退化。

### 测试结论模板

报告页会根据当前筛选数据生成风险摘要，主要依据：

- 是否存在超阈采样点
- 各指标峰值出现在哪个数据源和场景
- 是否存在疑似内存泄漏
- 配置建议模块生成的最低配置和推荐配置

这些结论是“规则生成”的初步判断，适合做测试报告草稿。正式结论仍建议结合业务场景、用户规模和低配机器实测结果确认。

## CPU 核数估算需要哪些数据

当前 Excel 里的 CPU% 可以支持“总体 CPU 需求”的初步估算，但它有局限：如果只有总 CPU%，无法判断应用是否存在单线程瓶颈、是否充分利用多核、是否被 IO 等待拖慢。

如果你的 CPU 数据来自：

```python
process.cpu_percent(interval=1) / psutil.cpu_count(logical=True)
```

它的口径接近 Windows 任务管理器“详细信息”里的进程 CPU 列，表示该进程占整机总 CPU 能力的百分比。这个口径可以用于当前配置建议公式。

不要把系统总 CPU 再除以 CPU 核数。如果使用的是：

```python
psutil.cpu_percent(interval=1)
```

它本身已经是整机 CPU 总利用率，通常范围是 0% 到 100%。

### CPU 配置估算方法

当前配置建议使用 CPU P95，而不是 CPU 均值或单次峰值：

```text
CPU原始需求 = 测试机逻辑核数 × CPU P95 / 目标CPU利用率上限
```

含义：

- 测试机逻辑核数：采集数据时机器的逻辑 CPU 数量
- CPU P95：当前筛选场景中，进程占整机 CPU 的 95 分位值
- 目标CPU利用率上限：希望目标机器长期运行时 CPU 不超过多少，例如 70%

示例：

```text
测试机：8 逻辑核
CPU P95：56%
目标利用率上限：70%

CPU原始需求 = 8 × 56% / 70% = 6.4 核
```

然后向上取常见核数档位：

```text
6.4 核 -> 8 核
```

推荐配置会在最低配置基础上乘以安全系数，例如 1.5：

```text
8 核 × 1.5 = 12 核
```

### 为什么需要目标 CPU 利用率

最低配置不能按 100% CPU 利用率来估算。原因是 CPU 长期接近 100% 时，系统没有余量处理突发任务，响应时间容易抖动，后台任务也容易排队。

常见目标：

| 目标利用率 | 适用情况 |
|---|---|
| 60% | 对响应时间敏感，要求余量较大 |
| 70% | 通用推荐值 |
| 80% | 资源紧张但可接受一定抖动 |

### CPU 估算的局限

只有总 CPU% 时，无法判断这些问题：

- 是否单线程打满一个核心
- 是否存在多核利用不均衡
- 是否被磁盘或网络 IO 等待限制
- 是否因为锁竞争导致 CPU 不高但响应慢
- 是否高 CPU 只出现在极短时间尖峰

因此页面会给出“基于当前数据的建议配置”，而不是绝对结论。

更准确的 CPU 配置建议，建议补充这些数据：

| 数据 | 作用 |
|---|---|
| 测试机 CPU 核数 | 把 CPU% 换算成核心需求的基础 |
| 每核 CPU 使用率 | 判断是否存在单核打满、多核不均衡 |
| 进程 CPU 时间 | 更准确区分应用自身消耗和系统整体消耗 |
| 并发数 / 任务量 / 数据规模 | 把配置建议和业务容量绑定 |
| 响应时间 / 处理耗时 | 判断 CPU 是否已经影响用户体验 |
| 队列长度 / 积压量 | 判断资源不足是否造成任务堆积 |
| IO 等待 / 磁盘吞吐 / 网络吞吐 | 判断高 CPU 或低 CPU 是否由 IO 瓶颈引起 |

如果只有当前这些指标，也可以给出初步结论；如果要形成正式的最低配置说明，建议补充每核 CPU、业务负载量和响应时间。

## 后续分析维度建议

当前工具已经支持核心指标和动态扩展指标，因此后续增强的重点不应只是“支持更多列名”，而是补充更能形成测试判断的分析口径。优先考虑持续性、尾部风险、版本退化、业务归一化和阶段化分析。

### 已落地：不依赖新增采集字段的第一优先级

这些维度可以直接基于现有时间序列计算，改动成本低，结论价值高，当前已经在概览、对比、基准增长、泄漏检测、版本对比和报告中落地。

| 分析维度 | 输出内容 | 必要性 |
|---|---|---|
| P90 / P99 | 每个场景、每个指标的分位值 | P95 已能描述高水位，P99 更适合观察尾部风险 |
| 超阈占比 | `超阈点数 / 总采样点` | 比超阈次数更公平，避免长场景天然告警次数更多 |
| 最大连续超阈时长 | 例如 CPU 连续超过 80% 持续 3 分钟 | 区分短暂尖峰和持续压力 |
| 峰值发生时间 | 峰值出现在场景开始后的第几分钟 | 判断问题集中在启动期、稳定期还是压力阶段 |
| 波动性 | 标准差、IQR、变异系数 | 判断资源是否稳定，适合 CPU、FPS、响应时间等指标 |
| 趋势斜率 | CPU、线程、句柄、IO 随时间变化的斜率 | 内存之外，也能发现线程泄漏、句柄泄漏或资源爬升 |

第一轮已实现的重点是：

```text
P99 + 超阈占比 + 最大连续超阈时长 + 版本退化判定
```

这些能力让报告从“展示数据”进一步升级为“给出判断”。

### 已落地：需要补充采集字段的第二优先级

这些维度需要 Excel 中增加业务或系统字段。它们的价值在于把资源消耗和业务负载绑定，避免只看资源高低。当前已经支持常见字段识别，并提供资源效率页面和报告章节。

| 分析维度 | 推荐字段 | 价值 |
|---|---|---|
| 业务吞吐 | QPS、TPS、任务数、处理条数 | 判断单位业务量消耗了多少资源 |
| 并发规模 | 并发用户数、连接数、任务并行数 | 判断资源随负载增长是否接近线性 |
| 响应质量 | 平均响应时间、P95 响应时间、错误数 | 判断资源压力是否已经影响用户体验 |
| 渲染性能 | FPS、卡顿次数、丢帧率 | 客户端或图形类应用更需要关注 |
| GC / 回收 | GC 次数、GC 耗时、堆内存 | Java、ArkTS、JS、.NET 等运行时应用较有价值 |
| 网络 | 上行、下行、请求数、失败数、重试数 | 解释 IO、响应时间或错误率异常 |
| 磁盘 | 读写吞吐、IOPS、IO wait | 当前 `io` 字段语义较泛，正式分析时最好拆开 |

补充这些字段后，页面会进一步计算资源效率指标：

```text
单请求 CPU 成本 = CPU P95 / QPS
单任务内存成本 = 内存峰值 / 并发任务数
单位吞吐 IO 成本 = IO 吞吐 / TPS
```

例如新版本 CPU 从 40% 增长到 50%，单看资源像是退化；但如果 QPS 从 100 增长到 180，则单位吞吐成本可能反而下降。

### 已落地：决策型分析的第三优先级

这类能力不是新增原始指标，而是把已有指标转换成更直接的测试结论。当前已经通过“决策”页和报告中的决策章节落地。

| 分析能力 | 作用 |
|---|---|
| 版本退化判定 | 自动标记 CPU、内存、线程、句柄、响应时间等指标是否相对基准版本明显退化 |
| 场景风险评级 | 每个场景输出低、中、高风险，便于报告汇总 |
| 发布门禁 | 根据阈值、退化比例、错误数判断是否满足发布要求 |
| 容量估算 | 基于并发数、吞吐量和资源水位推导不同业务规模下的机器配置 |
| 稳定性评分 | 综合泄漏、超阈、波动、错误率给出稳定性判断 |
| 瓶颈提示 | 粗略判断更像 CPU、内存、IO、网络还是业务错误导致的问题 |

版本退化判定在“版本对比”页完成；场景风险评级、发布门禁、容量估算、稳定性评分和瓶颈提示在“决策”页完成。

示例规则：

| 规则 | 判断 |
|---|---|
| CPU P95 增长 > 15% | 性能退化 |
| 内存峰值增长 > 10% | 内存退化 |
| 线程峰值增长 > 20% | 线程风险 |
| 句柄峰值增长 > 20% | 句柄风险 |
| P99 响应时间增长 > 20% | 体验退化 |
| 错误数增长 > 0 | 稳定性风险 |

### 取舍原则

后续扩展应优先选择能改变测试结论的维度，而不是单纯增加图表数量。

- 优先做持续性判断：超阈占比、连续超阈时长。
- 优先做尾部风险：P99、峰值发生时间。
- 优先做版本退化：自动判断相对基准版本是否不可接受。
- 有业务字段后再做归一化：QPS、并发数、任务量、响应时间。
- 谨慎让动态扩展指标参与配置建议：未知指标语义不清，不应自动影响最低配置推导。

- 原生 PDF 导出
- 报告中嵌入趋势图和对比图
- 支持用户保存阈值和字段映射配置
- 支持按测试阶段标记预热期、稳定期、压测期
