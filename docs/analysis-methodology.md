# 分析方法与原理说明

本文档解释 perf-analyzer 报告和图表中出现的主要分析方法、技术名词和推导逻辑。目标读者是不熟悉性能分析或时序分析的人：读完后，应能理解报告里的结论是怎么来的、每个指标该怎么看、哪些结论可以直接采信、哪些结论还需要结合业务验证。

## 1. 先理解这类数据

perf-analyzer 处理的是时间序列数据。时间序列可以理解为“按时间顺序记录的一串测量值”。

一条典型记录包含：

| 字段 | 含义 | 例子 |
|---|---|---|
| 时间戳 | 这条数据是什么时候采集的 | `2026-06-13 09:00:00.123` |
| 数据源 | 这份数据来自哪个文件、版本或批次 | `v1.0.xlsx` |
| 场景 / 分组 | 当前采样属于哪个测试场景 | `轻载`、`重载`、`设备A` |
| 指标 | 被测量的数值 | CPU、内存、温度、压力、响应时间 |

分析的基本问题是：

- 当前值高不高？
- 是偶发尖峰，还是持续异常？
- 和其他场景、版本相比有没有变差？
- 随时间是否持续上升或下降？
- 数据采集本身是否可靠？
- 如果按目标吞吐放大，资源需求大概是多少？

## 2. 数据处理流程

应用里的分析大致按下面流程执行：

```text
上传 Excel
  -> 识别时间戳、场景、指标字段
  -> 清洗为统一字段：source / scene / timestamp / metric columns
  -> 可选裁剪预热期，得到稳定区间
  -> 按数据源 + 场景分组
  -> 计算统计、趋势、异常、风险、报告
```

“预热期”是每个场景刚开始运行的一段时间。很多系统刚启动时会加载缓存、初始化连接、创建线程，这段数据不一定代表稳定运行状态。应用支持排除每个场景开头 N 分钟，使后续统计更接近日常稳定表现。

## 3. 常用统计口径

### 均值

均值就是平均值：

```text
均值 = 所有有效采样值之和 / 有效采样点数量
```

它适合描述整体水平。例如 CPU 均值 35%，表示这段时间整体负载不高。

局限是均值会掩盖尖峰。如果 99 个点都是 20%，1 个点是 100%，均值只有 20.8%，但那 1 个尖峰仍可能造成卡顿。

### 峰值

峰值就是最大值：

```text
峰值 = max(所有有效采样值)
```

它适合定位极端风险。例如内存峰值是否接近机器上限、响应时间是否出现过明显卡顿。

局限是峰值可能只是一次偶发采样，不一定代表常态。因此峰值通常要和 P95、异常持续时间一起看。

### P90 / P95 / P99

P95 是 95 分位值。把所有采样值从小到大排序后，位于 95% 位置附近的值就是 P95。

直观理解：

```text
P95 = 有 95% 的采样点不超过这个值
```

如果 CPU P95 = 78%，表示大多数时间 CPU 都在 78% 以下，只有约 5% 的采样点更高。

P90、P95、P99 都是“高水位”口径：

| 口径 | 含义 | 适合用途 |
|---|---|---|
| P90 | 90% 的点不超过该值 | 看比较稳健的高位水平 |
| P95 | 95% 的点不超过该值 | 常用性能容量口径 |
| P99 | 99% 的点不超过该值 | 看尾部风险和极端体验 |

为什么报告常用 P95：它比均值更能反映高水位，又比峰值更不容易被单个异常点带偏。

### 标准差

标准差衡量数据围绕均值波动的程度。

简化理解：

```text
每个点和均值的距离 -> 平方 -> 求平均 -> 开平方
```

标准差越大，说明波动越明显。CPU 从 30% 到 90% 来回跳，标准差通常会比一直在 60% 附近更大。

### IQR

IQR 是四分位距：

```text
IQR = P75 - P25
```

它描述中间 50% 数据的跨度。IQR 比标准差更不容易被极端值影响，适合观察常态波动。

### 变异系数

变异系数用于比较不同量级指标的相对波动：

```text
变异系数(%) = 标准差 / 均值 * 100
```

例如两个指标标准差都是 10，但一个均值是 100，一个均值是 1000。前者波动 10%，后者波动 1%，风险含义不一样。

## 4. 阈值、上下限和异常点

阈值是判断某个采样点是否异常的规则。

### 单阈值

单阈值适合“越高越差”或“越低越差”的指标。

越高越差：

```text
异常 = 指标值 > 阈值
```

例子：CPU 超过 80%、响应时间超过 1000ms。

越低越差：

```text
异常 = 指标值 < 阈值
```

例子：FPS 低于 45、QPS 低于目标值。

### 上下限正常区间

有些指标不是越高越差，也不是越低越差，而是需要落在一个合理区间内。此时使用 `lower_threshold` 和 `upper_threshold`。

```text
异常 = 指标值 < lower_threshold 或 指标值 > upper_threshold
```

例子：

- FPS 正常区间 45 到 120，低于 45 表示卡顿，过高可能表示采集口径异常。
- 某个传感器压力正常区间 20 到 80，低于或高于都需要关注。

如果同一指标同时配置了上下限和单阈值，应用优先使用上下限正常区间判断异常。

### 超阈次数

```text
超阈次数 = 被判定为异常的采样点数量
```

它回答“异常出现了多少次”。

### 超阈占比

```text
超阈占比(%) = 超阈次数 / 有效采样点数量 * 100
```

它比超阈次数更公平。因为采样时间越长，采样点越多，超阈次数天然可能更多；超阈占比能把不同长度场景放到同一比例口径比较。

### 偏离阈值比例

异常时间轴里点的大小会使用偏离比例：

```text
偏离比例 = |指标值 - 阈值| / |阈值| * 100%
```

对于上下限：

```text
低于下限 = |下限 - 指标值| / |下限| * 100%
高于上限 = |指标值 - 上限| / |上限| * 100%
```

偏离比例越大，说明异常程度越重。

## 5. 异常段和连续超阈

单个异常点只能说明“某一刻异常”。异常段用于回答“异常持续了多久”。

应用会先找出同一数据源、同一场景、同一指标下的异常点，然后把时间上连续的异常点合并为一个异常段。

合并逻辑：

```text
典型采样间隔 = 相邻时间戳间隔的中位数
最大允许断点 = 典型采样间隔 * 1.5

如果两个异常点的时间间隔 <= 最大允许断点
  -> 认为属于同一异常段
否则
  -> 分成两个异常段
```

异常段持续时长：

```text
持续时长 = 异常段最后时间 - 异常段开始时间 + 典型采样间隔
```

为什么要加一个典型采样间隔：采样点代表的是一个时间片，而不是一个没有长度的瞬间。加上采样间隔后，更接近“这段异常覆盖了多久”。

判断时要注意：

- 峰值超阈 1 次，通常低于连续超阈 5 分钟的风险。
- 连续超阈说明系统可能长期处于压力区。
- 异常段很多但都很短，可能是噪声、采集抖动或短时业务尖峰。

## 6. 趋势斜率和线性回归

趋势斜率用于判断指标是否随时间持续上升或下降。

应用把时间转换成“从场景开始到当前采样点经过了多少分钟”，然后拟合一条直线：

```text
y = a * x + b
```

其中：

- `x` 是经过的分钟数
- `y` 是指标值
- `a` 是趋势斜率
- `b` 是截距

趋势斜率的含义：

```text
趋势斜率 = 每分钟平均变化多少指标值
```

例子：

- 内存斜率 = 3 MB/分钟，表示内存平均每分钟上涨 3 MB。
- 线程斜率 = 0.2 个/分钟，表示线程数长期缓慢增加。
- CPU 斜率接近 0，表示 CPU 没有明显上升或下降趋势。

### R2

R2 衡量这条直线解释数据变化的程度。

直观理解：

```text
R2 越接近 1，说明数据越像一条稳定上升或下降的直线。
R2 越接近 0，说明数据很散，直线解释力弱。
```

应用里的内存泄漏判断会同时看斜率和 R2。因为只看斜率容易误判：如果数据大幅上下波动，刚好首尾变高，也可能算出正斜率，但不一定是持续泄漏。

## 7. 内存泄漏趋势检测

内存泄漏在这里不是直接证明“代码里有泄漏”，而是检测“内存是否持续增长，且增长趋势比较明显”。

判断逻辑：

```text
如果有效数据不足
  -> 数据不足
否则如果 内存斜率 >= 配置的泄漏斜率阈值 且 R2 >= 0.35
  -> 疑似泄漏
否则如果 内存斜率 > 0
  -> 轻微增长
否则
  -> 无明显增长
```

默认斜率阈值单位是 MB/分钟。

例子：

```text
内存斜率 = 2.5 MB/分钟
测试持续 60 分钟
推算增长约 150 MB
```

如果这种增长在长时间运行中持续存在，就可能导致内存不断逼近上限。

需要注意：

- “疑似泄漏”是风险提示，不是代码级定责。
- 短测试容易误判，长时间稳定性测试更可信。
- 缓存预热、批处理积压、数据加载也可能造成内存上升。

## 8. 滚动均值趋势

滚动均值用于平滑曲线，减少瞬时噪声。

按采样点数的滚动均值：

```text
当前点滚动均值 = 最近 N 个采样点的平均值
```

按时间窗口的滚动均值：

```text
先根据当前场景的中位采样间隔，把时间窗口换算成采样点数
再计算最近 N 个点的平均值
```

窗口越大，曲线越平滑，但短时间尖峰会被弱化。窗口越小，越接近原始数据，但噪声也更多。

推荐读法：

- 原始曲线尖峰多，滚动均值稳定：更像短时抖动。
- 原始曲线和滚动均值一起上升：更像持续压力或资源爬升。
- 滚动均值突破阈值：比单点突破更值得关注。

## 9. 上下限区间带

趋势图里的区间带有两种来源：

| 模式 | 来源 | 用途 |
|---|---|---|
| 配置上下限 | JSON 配置里的 `lower_threshold` / `upper_threshold` | 展示业务或测试定义的正常范围 |
| 自动 P5-P95 | 当前筛选数据的 P5 和 P95 | 展示这批数据自己的常见波动范围 |

配置上下限回答：“是否超出我预先定义的正常范围？”

自动 P5-P95 回答：“当前点是否明显偏离这批数据的大多数表现？”

自动 P5-P95 不是业务阈值，不能替代真实验收标准。它更适合探索数据分布。

## 10. 控制图 UCL / LCL

控制图用于发现“相对自身历史波动而言是否异常”。

应用当前使用三倍标准差控制限：

```text
中心线 = 均值
UCL = 均值 + 3 * 标准差
LCL = 均值 - 3 * 标准差
```

其中：

- UCL 是 Upper Control Limit，上控制限
- LCL 是 Lower Control Limit，下控制限

如果某个点超过 UCL 或低于 LCL，说明它相对这段序列的正常波动范围很异常。

控制图和业务阈值不同：

| 项目 | 业务阈值 | 控制图 |
|---|---|---|
| 依据 | 人为配置、验收标准、SLA | 当前数据自身的均值和波动 |
| 回答 | 有没有违反标准 | 有没有偏离自身常态 |
| 例子 | CPU > 80% 算异常 | CPU 比这段历史波动高很多 |

一个点可能没有超过业务阈值，但超过控制限。这说明它虽然还没违规，但已经偏离常态，值得观察。

## 11. 箱线图和离群点

箱线图用于观察分布。

常见组成：

| 名词 | 含义 |
|---|---|
| 中位数 | 排序后中间位置的值 |
| Q1 / P25 | 25% 位置的值 |
| Q3 / P75 | 75% 位置的值 |
| IQR | Q3 - Q1 |
| 离群点 | 明显远离主体分布的点 |

箱线图适合回答：

- 哪个场景整体更高？
- 哪个场景波动更大？
- 有没有少量极端点？
- 同一个指标在不同场景下分布是否明显不同？

## 12. 相关性热力图

相关性热力图展示指标之间的线性相关系数。

相关系数范围：

```text
-1 到 1
```

| 值 | 含义 |
|---|---|
| 接近 1 | 两个指标倾向一起上升或一起下降 |
| 接近 -1 | 一个上升时另一个倾向下降 |
| 接近 0 | 没有明显线性关系 |

重要限制：相关不等于因果。

例如 CPU 和响应时间相关，只能说明它们经常一起变化，不能直接证明 CPU 一定导致响应变慢。可能是业务流量同时推高了 CPU 和响应时间。

## 13. 采样间隔和数据质量

采样间隔是同一数据源、同一场景内相邻时间戳的差：

```text
采样间隔 = 当前采样时间 - 上一个采样时间
```

应用会统计：

- 中位采样间隔：典型采样频率
- P95 采样间隔：大多数间隔不超过多长
- 最大采样间隔：是否存在明显采集缺口
- 重复时间戳：是否多条记录时间相同
- 乱序次数 / 负采样间隔：数据是否没有按时间递增
- 是否包含毫秒 / 亚秒：时间戳精度是否高于秒

采样间隔异常通常表示：

- 采集工具卡顿
- 数据上传中断
- Excel 导出缺点
- 采样频率不稳定

数据质量会影响分析可信度。比如采样间隔很不均匀时，超阈次数和趋势斜率仍可参考，但持续时长需要更谨慎。

## 14. 资源效率

资源效率把资源消耗除以业务量，用于判断“每单位业务消耗多少资源”。

应用会优先选择吞吐口径：

```text
qps -> tps -> task_count -> request_count
```

常见公式：

```text
CPU P95/吞吐 = CPU P95 / 平均吞吐
IO P95/吞吐 = IO P95 / 平均吞吐
网络KBps/吞吐 = 平均网络流量 / 平均吞吐
内存峰值/并发 = 内存峰值 / 平均并发
失败率(%) = 失败请求数 / 请求数 * 100
每千请求错误数 = 错误数 / 请求数 * 1000
```

这些口径能避免只看资源绝对值。

例子：

- A 场景 CPU P95 是 70%，QPS 是 100。
- B 场景 CPU P95 是 80%，QPS 是 300。

只看 CPU，B 更高；但按每 QPS 消耗，B 可能更高效。

## 15. 配置建议

配置建议用于估算当前测试结果对应的最低配置和推荐配置。

CPU 估算使用 P95 CPU，而不是均值：

```text
CPU原始需求(核) = 测试机核数 * (CPU P95 / 100) / 目标CPU利用率
```

例子：

```text
测试机 8 核
CPU P95 = 70%
目标CPU利用率 = 70%

CPU原始需求 = 8 * 70% / 70% = 8 核
```

如果目标利用率设为 50%：

```text
CPU原始需求 = 8 * 70% / 50% = 11.2 核
```

然后应用会向上取常见 CPU 核数档位，例如 12、16、24。

内存估算：

```text
内存原始需求 = 应用内存峰值 + 系统预留内存
```

然后向上取常见内存档位，例如 8GB、16GB、32GB。

推荐配置会在最低配置基础上乘以安全系数，再向上取档位。

## 16. 容量估算和容量曲线

容量估算回答：“如果目标吞吐变成 50、100、200，需要多少 CPU 和内存？”

它使用当前数据的单位资源成本做线性外推。

CPU 单位成本：

```text
CPU单位成本 = CPU P95 / 平均吞吐
```

应用会取多个场景 CPU 单位成本的 P95，作为偏保守的单位成本：

```text
CPU单位成本P95 = P95(CPU P95/吞吐)
```

目标吞吐下需要的 CPU 百分比：

```text
目标CPU百分比 = CPU单位成本P95 * 目标吞吐
```

换算为 CPU 核数：

```text
CPU需求(核) = 测试机核数 * (目标CPU百分比 / 100) / 目标CPU利用率
```

内存估算先推算目标并发：

```text
并发/吞吐比例 = 总平均并发 / 总平均吞吐
目标并发 = 目标吞吐 * 并发/吞吐比例
```

再推算内存：

```text
内存需求(GB) = 内存峰值/并发的P95 * 目标并发 / 1024 + 系统预留内存GB
```

容量曲线就是把多个目标吞吐分别计算一遍，然后画出：

- 目标吞吐越高，建议 CPU 核数如何变化
- 目标吞吐越高，内存需求如何变化

为什么看起来需要很多核：容量估算会按 P95 单位成本、目标 CPU 利用率和常见核数档位向上取整。它偏保守，目的是给稳定运行留余量，不是证明当前机器一定不够。

容量估算的前提：

- 当前测试能代表目标业务模型。
- 吞吐、并发、资源消耗之间近似线性。
- 数据里有有效的 QPS/TPS/任务数/请求数和并发字段。

如果业务扩大后出现锁竞争、数据库瓶颈、缓存击穿、网络限制，线性外推会失真。因此容量曲线适合做初步规划，正式配置仍应做目标规模压测。

## 17. 场景风险评分

场景风险评分把多个风险项合成一个分数。

主要输入包括：

- 最大超阈占比
- 最长连续超阈
- 内存趋势
- 失败率
- 每千请求错误数
- 响应时间 P95
- FPS P95

单项风险会按 warning / critical 两档加分：

```text
正常 = 0 分
达到 warning = 1 分
达到 critical = 2 分
```

其中内存疑似泄漏会额外加重。

风险等级：

```text
风险评分 >= 7 -> 高风险
风险评分 >= 3 -> 中风险
否则 -> 低风险
```

风险评分适合做排序和汇总，不适合替代最终业务判断。比如某个后台批处理场景响应时间高，可能是可接受的；但前台交互场景同样响应时间就可能不可接受。

## 18. 稳定性评分

稳定性评分由风险评分换算：

```text
稳定性评分 = max(0, 100 - 风险评分 * 10)
```

等级：

| 分数 | 等级 |
|---|---|
| >= 85 | 优秀 |
| >= 70 | 可接受 |
| >= 50 | 需关注 |
| < 50 | 高风险 |

它的意义是把风险评分换成更容易读的 0 到 100 分。

## 19. 发布门禁

发布门禁是规则判断，不是模型预测。

常见规则包括：

- 场景风险等级不高于某个上限。
- 不允许疑似内存泄漏。
- 不允许任何超阈采样点。
- 不允许请求失败。

只要启用的规则中有一条失败，整体门禁就是不通过。

发布门禁适合自动化验收，但规则需要按项目实际调整。测试环境、业务场景、低配目标机、SLA 不同，门禁标准也应该不同。

## 20. 风险雷达图

雷达图把不同风险维度统一转换成 0 到 100 的风险分，方便看场景画像。

常见维度：

| 维度 | 大致含义 |
|---|---|
| CPU压力 | CPU P95 相对 CPU 阈值的比例 |
| 内存压力 | 内存占比 P95 相对内存阈值的比例 |
| IO压力 | IO P95 相对 IO 阈值的比例 |
| 响应风险 | 响应时间 P95 相对 1000ms 的比例 |
| 错误风险 | 失败率相对 1% 的比例 |
| 流畅风险 | FPS 低于 60 的程度 |
| 稳定风险 | 场景风险评分换算后的风险程度 |

雷达图适合看“风险形状”：

- CPU 维度突出：偏 CPU 压力。
- 内存和稳定风险突出：可能存在资源爬升。
- 响应风险突出但资源压力不突出：可能是外部依赖、锁等待、网络或业务逻辑问题。

## 21. 版本对比和退化幅度

版本对比用于判断新版本是否比基准版本变差。

增长率：

```text
增长率(%) = (当前值 - 基准值) / 基准值 * 100
```

对于越高越差的指标，增长就是退化：

```text
退化幅度 = 增长率
```

例如响应时间从 800ms 到 1000ms：

```text
增长率 = (1000 - 800) / 800 * 100 = 25%
退化幅度 = 25%
```

对于越低越差的指标，方向要反过来：

```text
退化幅度 = -增长率
```

例如 FPS 从 60 降到 45：

```text
增长率 = (45 - 60) / 60 * 100 = -25%
退化幅度 = 25%
```

这样处理后，所有指标都统一成“退化幅度越大越差”。

## 22. 瓶颈提示

瓶颈提示是基于规则的初步判断。

常见规则：

- CPU P95 接近 CPU 阈值：提示 CPU 压力。
- 内存占比 P95 接近内存阈值：提示内存压力。
- IO P95 接近 IO 阈值：提示 IO 压力。
- 响应时间高且网络流量大：提示网络压力。
- 存在失败请求或错误：提示业务错误 / 重试。
- 响应慢但资源压力不明显：提示可能不是本机资源瓶颈。

瓶颈提示适合引导排查方向，不能直接作为根因结论。真正定位还需要结合日志、链路追踪、系统监控和业务上下文。

## 23. 通用时序模式如何理解

通用时序模式不要求指标必须是 CPU、内存、QPS。只要有时间戳和数值列，就可以按相同方法分析。

例子：

| 场景 | 指标 | 可用分析 |
|---|---|---|
| 传感器 | 温度、湿度、压力 | 趋势、区间异常、控制图、采样间隔 |
| 质量检测 | 尺寸、重量、误差 | 上下限、箱线图、控制图、异常段 |
| 实验记录 | 浓度、电压、电流 | 趋势斜率、相关性、异常时间轴 |
| 设备监控 | 转速、振动、功率 | P95、波动性、控制图、瓶颈提示 |

需要注意：通用时序模式只知道“数值变化”，不知道业务语义。比如温度越高越差还是越低越差，需要通过阈值方向或上下限配置告诉应用。

## 24. 如何按报告一步步分析

推荐顺序：

1. 先看数据质量：时间戳是否正常、采样间隔是否稳定、是否有大量空值。
2. 看测试结论：有没有超阈、疑似泄漏、发布门禁失败。
3. 看汇总数据：关注 P95、峰值、超阈占比、最大连续超阈。
4. 看趋势图：判断异常是瞬时尖峰还是持续高水位。
5. 看异常页：定位具体时间、场景、指标和异常段。
6. 看分布和控制图：判断波动是否异常，是否存在离群点。
7. 看资源效率：如果有吞吐和并发，分析单位业务成本。
8. 看决策页：用风险评分、雷达图、容量曲线辅助汇报。
9. 看版本对比：确认新版本是否相对基准退化。
10. 最后结合业务：判断这些风险是否影响用户、SLA 或发布标准。

## 25. 常见误读

| 误读 | 正确理解 |
|---|---|
| 峰值高就一定有问题 | 还要看持续时间、P95 和业务影响 |
| 均值低就说明没问题 | 均值可能掩盖短时尖峰 |
| P95 比峰值低，所以不用管峰值 | P95 看常态高水位，峰值看极端风险，两者都要看 |
| 相关性高说明 A 导致 B | 相关不等于因果，只能提示排查方向 |
| 控制图超限等于业务违规 | 控制图看相对自身波动，业务阈值看验收标准 |
| 疑似泄漏就是代码泄漏 | 只是内存持续增长风险，需要结合长测和代码排查 |
| 容量曲线给出的核数就是最终采购配置 | 它是线性外推建议，最终要目标规模压测验证 |
| 通用时序模式能自动理解所有指标好坏 | 指标方向和正常区间仍需要配置 |

## 26. 报告结论的可信边界

应用输出的是“基于规则和统计的分析草稿”。它适合：

- 快速发现异常时间段。
- 横向比较场景或版本。
- 生成测试报告初稿。
- 给出容量和配置的初步估算。
- 帮助非性能专家读懂时序数据。

它不直接替代：

- 线上 SLA 结论。
- 根因定位。
- 正式容量压测。
- 代码级性能诊断。
- 业务可接受性判断。

更可靠的结论通常需要同时满足：

- 数据采样稳定。
- 测试时长足够。
- 场景能代表真实业务。
- 阈值符合业务目标。
- 多次测试结论一致。
- 关键风险能被日志、监控或复测验证。
